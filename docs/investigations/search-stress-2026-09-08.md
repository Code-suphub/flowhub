# 搜索性能回归基线（2026-09-08）

在本机 Codex 内置 Chromium 152 中，使用仓库 `app/scripts/search-stress/serve.py` 加载当前生产前端及合成数据。未读取真实剪贴板。启动本地服务器后点击 Run stress，再点击 Run paging checks。

这些数据是浏览器前端同步执行与强制布局的耗时，不是原生快捷键到 WebKit 显示延迟；测试中使用直接函数调用，不包含输入防抖和真实数据库／IPC。每组仅 5 次，最大值不能当作可靠的总体 p95。

| 全部切换至剪贴板的数据量 | 中位数 | 最大值 | DOM 结果行 |
| --- | ---: | ---: | ---: |
| 30 | 6.5ms | 9.3ms | 30 |
| 300 | 2.6ms | 4.5ms | 20 |
| 1000 | 5.0ms | 6.3ms | 20 |
| 3000 | 4.3ms | 5.3ms | 20 |

- 14 万字符记录：切换与布局 7.4ms，实际结果 DOM 文本约 9907 字符。
- 模拟一来源 900ms、其余 20ms：首个快结果进入 DOM 26ms，全部完成 905ms。说明快结果没有等待最慢来源；不代表真实网络查询速度。
- 全部模式连续加载 250 次：3000 条、3000 个唯一键，无重复丢失；循环观测 DOM 结果行最多 78；总耗时 1696.1ms（含脚本插入的帧等待）。
- 剪贴板滚动至末尾索引 2999，再回顶部索引 0；键盘定位索引 1200 可见。

结论：此次合成前端基线没有发现 DOM 随 3000 条数据线性增长，也没有复现慢来源阻塞首批结果。不能据此排除真实 WebKit 的唤出、图片处理、IPC、内存长期增长与显示合成卡顿。后续应补实际输入分阶段计时与长时间真实环境采样。
