# 本机原生搜索采样（2026-09-08）

## 环境与方法

直接运行 `/Applications/FlowHub.app`，实际 WebKit 引擎 `AppleWebKit/605.1.15`，本机剪贴板数据库 2406 条记录。未替换任何搜索来源，剪贴板／应用调用现有 Tauri IPC，网页／备忘运行现有本地索引。

CUA 连接已安装 FlowHub 的辅助功能树两次超时，因此增加显式 `--search-diagnostics` 本地入口。在已运行的应用中注入固定的内置诊断脚本，触发生产 input 监听器、范围切换和分页，结果写入剪贴板存储目录 `diagnostics/search-native-latest.json`。不保存结果正文、查询值或 URL，不修改配置或激活／粘贴结果。测试结束恢复原搜索词、范围、固定窗口状态和采样开关对应的内存测量状态。

这是真实 WebKit + 本地数据链路采样，但输入是程序触发，范围及分页通过生产函数调用，不包括硬件键盘／鼠标、系统事件分发、全局快捷键及窗口首次唤出。下一帧回调不是系统实际呈现帧率。没有声称双屏全屏已验收。

## 第一轮

版本 `0.1.7-local.20260908013752`。15 个输入场景、25 次范围切换，约 19.7 秒。

- 普通范围调度约 180–181ms；网页独立范围约 1ms。
- 来源查询约 1–19ms；应用／剪贴板包含 IPC，网页／备忘主要为本地 JS。
- 首响应 DOM 多数 182–198ms；全部范围一次达到 255ms。
- 该次同步 render 达到 **62ms**，需要进一步拆分排序、HTML 生成、DOM 更新与布局，不能判定所有路径都流畅。
- 空查询切换剪贴板同步约 9–11ms，其他范围约 2–5ms。
- 首轮分页同时触发手动函数和滚动自动加载，出现重复空调用，因此 100 次调用不视为 100 次有效分页；该轮分页耗时不作结论。

## 复测调整

等待新查询来源完成后才读取输入计时。分页先确认所有来源查询一致，串行调用生产分页函数；统计实际增加的结果数量，遇到无进展停止。分页结束后另做 60 次程序滚动，每次等待两次 requestAnimationFrame，避免把重复分页调用冒充吞吐量。

诊断入口有并发保护、一次运行期间才接受报告，报告上限 256KiB。仅显式调用时运行，不随正常启动自动压测。

## 验证

9 组前端测试和 44 项 Rust 测试通过。报告反映采样结果，不代表性能问题已经修复。

### 确认的问题

1. **明显慢帧**：全部范围第二个固定搜索用例两轮 render 分别为 62ms／57ms。第二轮首响应虽然较早发布，后续来源发布仍发生慢 render，因此只看首响应指标会漏掉卡顿。下一步应拆分匹配排序、HTML 生成、DOM 写入与同步布局计时。
2. **全部分页不前进**：85 次有进展的加载后，最终显示 301 条；下一次无进展且 `hasMore=true`，四个来源查询均与当前输入一致。`refreshClipboard` 的追加 guard 仅允许 clipboard 范围、`refreshWeb` 的追加 guard 仅允许 web 范围，而 `loadMoreAll` 在 all 范围调用它们，追加请求被直接拒绝。这是实际入口组合问题，现有合成分页测试使用的 mock 没覆盖真实 guard。此轮只定位，没有修改这些 guard。
3. **固定等待明显**：原生查询通常远小于 180ms 防抖，普通范围的可感知搜索等待主要来自调度。不能直接将 180ms 归因于数据库；后续可独立评估本地来源的调度策略。

### 结论边界

确认真实卡顿与分页问题，未声称已修复。程序滚动期间 DOM 受控；未采集系统级合成跟踪或长时间内存趋势，因此不能以这些数据证明所有场景流畅。第一轮异常缺失样本通过等待来源完成后复测，第二轮 15 个输入均有来源计时。
