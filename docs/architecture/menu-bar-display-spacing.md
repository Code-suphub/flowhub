# 多屏菜单栏分隔项间距

## 当前方案：固定原生箭头，收起时才创建占位

用户在 `0.1.9-local.20260909074823` 再次复现收起后箭头丢失。16:01:17 和 16:01:20 的日志均显示离屏绘制有字形、坐标落在对应屏幕内，但用户桌面不可见；不能据此断言桌面显示正常。停止使用加宽的箭头项及自定义标签绘制方案。

箭头恢复为固定小尺寸 NSStatusBarButton 的原生 title，展开/收起只改变字符。展开时完全移除普通隐藏占位，图标不会被插到箭头与一个一像素分界之间；收起时才在箭头左侧建立独立的超宽隐藏占位，展开即销毁。始终隐藏分界仍保留。这个方案并非“所有状态都只有一个原生项”，而是优先恢复可靠的箭头显示，同时消除展开整理时的额外分界。

诊断保留，但 glyph 几何改为原生 cell 的 titleRect，绘制快照改为小尺寸原生按钮，不再采集自定义标签。下面合并方案及其测试结果是排查历史，不代表当前实现。

`0.1.9-local.20260909080600` 安装后，用户确认箭头显示恢复正常。自动化测试通过，普通运行日志确认已使用原生 title 和小尺寸按钮。

## 2026-09-09：箭头与普通隐藏边界合并

普通隐藏区现在直接以箭头的 NSStatusItem 为边界。展开时使用短宽度，收起时增宽；项内部用固定在右侧的 NSTextField 绘制箭头，鼠标事件层在其上方并随按钮宽度自动调整。普通分界与箭头共用同一 window ID，图标不能再插到两个独立项之间。保留箭头原 autosave identity 和始终隐藏分界，旧的普通分界位置偏好不再读取，也不会创建对应状态项。

同时移除普通分界的重建补偿、250 ms 位置轮询及内部宽度约束修改。以下早期双分界间距方案仅作历史记录。

原生回归入口：退出已有 FlowHub 后，以 `FLOWHUB_TAURI_ORGANIZER_SMOKE_TEST=single-control` 启动本地构建。它通过 tray-icon 的原生 mouseUp 入口连续切换四次，等待 AppKit 布局后校验共享窗口、收起状态、按钮宽度、鼠标响应层宽度和箭头右侧坐标，并恢复原始状态。此测试不是物理鼠标操作，也不能替代所有显示器排列、刘海屏和跨屏拖动验收。

本地 `0.1.9-local.20260909065805` 验证：两轮原生回归均通过，分别记录到 scale=2 和 scale=1 的屏幕。展开时按钮及鼠标响应层宽度均为 26，收起时均为 5000，窗口 ID 在切换期间保持不变。第二轮加入临时 QA 状态项，在箭头左侧展开位置 x=1183/1180，收起后 x=-3810，连续两轮均能隐藏并恢复。临时状态项已退出，FlowHub 已恢复普通启动；98 项 Rust 测试及完整 npm test 通过。

随后用户实测发现收起后箭头文字消失：上述几何回归没有验证文字的实际绘制，不能证明箭头可见。修复不再依赖 NSStatusBarButton 的 title/alignment，改为同一按钮内部的右侧标签；回归增加绘制层存在及其右边缘与按钮右边缘重合的检查。标签不是新的 NSStatusItem，因此不会重新引入可拖入的独立分界。

`0.1.9-local.20260909071526`：完整测试通过。原生回归连续切换四次，标签坐标及 hitTest 命中鼠标响应层均通过；AppKit 缓存绘制导出的 18 pt 标签 PNG 已目视确认展开 `›`、收起 `‹` 均有可见字形。整屏截图未捕获应用状态图标，因此这次的视觉证据是实际标签绘制快照，不是物理桌面的完整验收。测试后已恢复普通启动。

## 普通运行中的箭头诊断

开启现有诊断开关后，`menu_bar_organizer` 的 `control.glyph` 记录绘制层存在、父级隐藏、alpha、bounds/visibleRect、裁剪状态、经过 NSView/NSWindow 坐标转换的屏幕矩形、屏幕相交情况及鼠标命中。每条布局记录带 PID 和版本，便于区分实际运行和旧测试进程。

切换后立即、150 ms、800 ms、3000 ms 采样；后两次另写 `menu_bar_organizer_glyph_render`，包括实际标签的 AppKit 缓存绘制结果、像素尺寸、非透明像素数、失败原因和 PNG 路径。快照位于活动存储目录的 `diagnostics/glyph-snapshots`，固定 16 个槽位，每张图对应 JSON 元数据；使用旧日志中的图片路径前需核对 `capturedAt`，因为槽位会覆盖。只捕获最大 64×64 point 的箭头标签，不捕获桌面、其他应用或剪贴板。编码后文件保存和像素统计在后台进行，关闭诊断时不采样。

`renderHasNonTransparentPixels` 只表示缓存绘制含非透明像素；`fullyInsideAssignedScreen` 只表示坐标落在对应屏幕内。这两者都不能证明最终桌面合成、跨屏镜像或遮挡结果，因此 `screenVisibilityConfirmed` 始终为 false，不能再把离屏绘制成功表述为真实桌面验收通过。

2026-09-07：展开时不再将 NSStatusItem.length 设为 0、停用内部约束并单独强制 window.setContentSize(1)。只保留原生布局并设置长度 1 的第一轮调整仍产生 17 point 宽度，用户确认两个屏幕都变宽。

当前实现：先 setLength(1)，随后将已经识别的 width-to-width 约束常量清零，保持约束启用。顺序重要，setLength 会重新写入 16 point 内边距。收起时仍 setLength(10000)，保留系统收起布局，不删除分界或改变隐藏区排序。只调整宽度约束，其他未知布局保持原状。仍使用 AppKit 内部约束，未来系统版本可能需要适配。

本地版本 0.1.6-local.20260907090625 安装启动后，expand:after_800ms 日志确认：约束 constant=0、status length=1、button width=1、window width=1；此前 window width=17。当前记录屏幕 scale=2。未将单窗口的尺寸测量视为两个屏幕的视觉验收。

36 项 Rust 测试与 6 组前端回归通过；最终布局调用顺序调整后本地 release 构建成功。后续双屏验收应来回激活两块屏幕，检查展开/收起、隐藏区顺序和箭头点击。诊断快照包含 screen frame、scale 和 boundaryPadding。

## 多屏重复条目

菜单栏枚举会包含多个菜单栏行。原 managed_menu_bar_items 将它们全部输出，并与单个分隔项横坐标比较，导致重复条目及错误分区。现以 boundary window 的 y 坐标选择同一菜单栏行（容差 1 point），并按 window_id 去重。操作前的库存复核同步采用这个范围；保留屏幕外隐藏项目，不按 owner_name 合并真实多图标。

新增回归验证跨行副本排除、同名不同窗口保留、屏幕外项目保留、重复 window_id 去重、分隔项缺失报错。37 项 Rust 测试及 6 组前端回归通过。该筛选针对不同菜单栏行；如果两个显示器顶边恰好重合、菜单栏 y 完全相同，还需额外的显示器归属信息才能严格区分副本。

## 连续隐藏/恢复的顺序

日志显示同一图标首次恢复采用 control 右侧默认锚点，下一次采用其他应用图标作邻居。原排序记录排除了所有 FlowHub 自有窗口，因此无法表达位于主图标左侧还是右侧。现将唯一可识别的主图标加入排序参照（仍不作为可移动条目），为该参照提供独立稳定身份；恢复邻居时同样纳入它。默认落点也启用相邻检查，不再只验证位于分区一侧。新增连续三轮 Visible / Hidden 分区恢复测试。

原有历史记录如果没有主图标参照，不能凭空恢复丢失的相对位置；后续隐藏时会按当前排序建立完整记录。当前双屏行筛选仍有前文所述相同 y 坐标的限制。
