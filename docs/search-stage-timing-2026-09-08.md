# 搜索分阶段计时（2026-09-08）

基线提交 `9527e95` 后增加测量。原来的搜索压测只有同步渲染及首结果总耗时，不能区分防抖和来源查询。

## 计时含义

`search-timing.js` 遵守本地诊断采样开关，启动／重新唤出时读取开关。在搜索窗口内存最多保留 100 次输入或范围切换，每次最多 100 个来源与渲染样本，不记录关键词、内容、URL 或错误消息。重新唤出时重置本窗口记录。关闭开关后重新唤出停止采样。

通过搜索窗口的开发者控制台读取 `window.flowhubSearchTiming.report()`；当前尚未接入设置页的“读取界面测量”，也不持久化到原生诊断日志。

- `dispatchMs`：输入事件起点到防抖回调启动，包含同步输入处理、配置的 180ms 等待及事件队列延迟。网页独立范围走动画帧调度，不固定等待 180ms。
- `sources[].startMs / durationMs`：来源调用的开始偏移与 Promise 耗时。真实应用包含 IPC、后端执行和返回解析，尚未拆分成纯数据库与 IPC。
- `sources[].status / stale`：成功、失败和结束时是否已被新输入替代。错误消息不进入记录。
- `renders[]`：同步 render 调用耗时，包含其中同步触发的布局；不包含其后异步图片加载或系统合成。
- `firstResponseDomMs`：第一个通过现有过期检查并应用到状态的来源响应，在随后 render 完成时的输入起点偏移。响应可为空，所以它不等同于“首个非空结果”。输入后旧缓存的初次 render 不计入该字段。纯缓存范围切换没有新响应时，此字段不设置。
- `nextFrameWaitMs`：上述 render 结束至下一次 requestAnimationFrame 回调的等待；不能证明已经实际绘制到屏幕。输入已变化或关闭测量时丢弃旧回调。

## 浏览器验证

本机 Chromium 152，隔离合成数据，生产搜索脚本。运行 `python3 app/scripts/search-stress/serve.py`，打开 localhost:8766，点击 **Run stage timing**。按钮用真实 input 事件进入生产查询调度；clipboard/web/memo 模拟 20ms，app 模拟 900ms。没有读取用户数据。

首次结果：

| 阶段 | 耗时 |
| --- | ---: |
| 输入至防抖回调 | 181.8ms |
| 剪贴板来源 | 21.6ms |
| 网页／备忘来源 | 21.3／21.2ms |
| 应用慢来源 | 901.2ms |
| 首响应进入 DOM（从输入起） | 217.6ms |
| 本次 render 最大耗时 | 13.5ms |
| 首响应 render 后下一帧等待 | 2.2ms |

第二轮：调度 182.2ms，快来源约 21.2ms，应用来源 900.6ms，首响应 DOM 204.4ms，同步 render 最大 0.8ms，下一帧等待 3.9ms。首轮 render 的 13.5ms 未在第二轮复现，不能凭两次样本判断长期卡顿。

验证了防抖与来源耗时分离，快来源发布没有等待 900ms 的慢来源。以上是合成延迟的测量链路验证，不是实际应用索引查询速度，也不是实际 WebKit 输入到屏幕呈现延迟。样本少，不报告总体 p95。
