# 多屏菜单栏分隔项间距

2026-09-07：展开时不再将 NSStatusItem.length 设为 0、停用内部约束并单独强制 window.setContentSize(1)。只保留原生布局并设置长度 1 的第一轮调整仍产生 17 point 宽度，用户确认两个屏幕都变宽。

当前实现：先 setLength(1)，随后将已经识别的 width-to-width 约束常量清零，保持约束启用。顺序重要，setLength 会重新写入 16 point 内边距。收起时仍 setLength(10000)，保留系统收起布局，不删除分界或改变隐藏区排序。只调整宽度约束，其他未知布局保持原状。仍使用 AppKit 内部约束，未来系统版本可能需要适配。

本地版本 0.1.6-local.20260907090625 安装启动后，expand:after_800ms 日志确认：约束 constant=0、status length=1、button width=1、window width=1；此前 window width=17。当前记录屏幕 scale=2。未将单窗口的尺寸测量视为两个屏幕的视觉验收。

36 项 Rust 测试与 6 组前端回归通过；最终布局调用顺序调整后本地 release 构建成功。后续双屏验收应来回激活两块屏幕，检查展开/收起、隐藏区顺序和箭头点击。诊断快照包含 screen frame、scale 和 boundaryPadding。

## 多屏重复条目

菜单栏枚举会包含多个菜单栏行。原 managed_menu_bar_items 将它们全部输出，并与单个分隔项横坐标比较，导致重复条目及错误分区。现以 boundary window 的 y 坐标选择同一菜单栏行（容差 1 point），并按 window_id 去重。操作前的库存复核同步采用这个范围；保留屏幕外隐藏项目，不按 owner_name 合并真实多图标。

新增回归验证跨行副本排除、同名不同窗口保留、屏幕外项目保留、重复 window_id 去重、分隔项缺失报错。37 项 Rust 测试及 6 组前端回归通过。该筛选针对不同菜单栏行；如果两个显示器顶边恰好重合、菜单栏 y 完全相同，还需额外的显示器归属信息才能严格区分副本。

## 连续隐藏/恢复的顺序

日志显示同一图标首次恢复采用 control 右侧默认锚点，下一次采用其他应用图标作邻居。原排序记录排除了所有 FlowHub 自有窗口，因此无法表达位于主图标左侧还是右侧。现将唯一可识别的主图标加入排序参照（仍不作为可移动条目），为该参照提供独立稳定身份；恢复邻居时同样纳入它。默认落点也启用相邻检查，不再只验证位于分区一侧。新增连续三轮 Visible / Hidden 分区恢复测试。

原有历史记录如果没有主图标参照，不能凭空恢复丢失的相对位置；后续隐藏时会按当前排序建立完整记录。当前双屏行筛选仍有前文所述相同 y 坐标的限制。
